## 1. 使用的系统与框架

- **环境变量加载**：通过 `io.github.cdimascio:dotenv`（`Dotenv`）读取根目录 `.env` 文件，并允许系统环境变量覆盖。
- **运行时能力编排**：使用自研的 `StageConfig` record + Builder 模式，以“阶段名”（s01~s17、s_full）为单位组合工具集、system prompt 模板和各子系统开关。
- **前端配置**：Next.js 工程通过 `next.config.ts`、`package.json`、`.env`（若存在）以及 `src/lib/constants.ts` 等文件管理前端构建与运行参数；多语言文案集中在 `web/src/i18n/messages/{en,ja,zh}.json`。

## 2. 关键文件与包

| 路径 | 作用 |
|---|---|
| `.env` | 存放 `ANTHROPIC_API_KEY`、`MODEL_ID`、`ANTHROPIC_BASE_URL` 等模型接入凭据 |
| `src/main/java/com/learnclaudecode/common/EnvConfig.java` | 统一的环境变量读取器，封装 `.env` 与系统环境变量的优先级 |
| `src/main/java/com/learnclaudecode/agents/StageConfig.java` | 定义全部教学阶段的配置记录与 Builder，集中声明每个阶段暴露的工具、system prompt 模板和子系统开关 |
| `src/main/java/com/learnclaudecode/Main.java` | 应用入口，默认启动 `SFull`（完整能力版本） |
| `src/main/java/com/learnclaudecode/agents/SFull.java` | 组装 `StageConfig.sFull()` 并驱动 AgentRuntime |
| `.team/config.json` | 团队配置（当前为空成员列表），供多 Agent 团队功能使用 |
| `web/next.config.ts`、`web/package.json` | Next.js 前端构建与运行配置 |
| `web/src/i18n/messages/*.json` | 前端多语言文案配置 |

## 3. 架构与设计约定

### 3.1 环境变量分层与优先级
`EnvConfig` 在构造时调用 `Dotenv.configure().ignoreIfMissing().load()`，随后按以下顺序解析任意 key：
1. `System.getenv(key)` —— 最高优先级，便于 CI、IDEA 运行配置直接覆盖。
2. `.env` 文件中同名键 —— 本地开发默认值来源。
3. 返回空 `Optional` —— 由调用方提供默认值或抛出异常。

必填项通过私有 `require("MODEL_ID")` 强制校验：缺失时抛出 `IllegalStateException("缺少环境变量: MODEL_ID")`。可选项如 `ANTHROPIC_API_KEY`、`ANTHROPIC_BASE_URL` 则回退到空串或 `https://api.anthropic.com`。

### 3.2 阶段化能力开关（Feature Flags）
`StageConfig` 是一个 Java record，包含 16 个布尔开关字段：`enableTodoNag`、`enableCompression`、`enableBackground`、`enableInbox`、`subagentWritable`、`autonomousTeammates`、`enablePermission`、`enableHooks`、`enableMemory`、`enableCron`、`enableMcp`、`enableWorkflow`、`enableGoalLoop` 等，配合 `tools`（工具定义列表）和 `systemTemplate`（system prompt 模板）共同描述一个阶段的完整行为。

每个阶段通过静态工厂方法（`s01()` ~ `s17()`、`sFull()`）用 Builder 链式装配，例如 s15 把 s01~s14 的所有能力开关打开并合并工具集，s16/s17 分别引入工作流和目标循环。新增阶段只需新增一个 `sXX()` 方法，无需修改已有逻辑——这是典型的“配置即演进”设计。

### 3.3 System Prompt 动态展开
`StageConfig.systemPrompt(SkillLoader, Path)` 会在运行时将模板中的 `${WORKDIR}` 替换为当前工作目录，`${SKILLS}` 替换为 `SkillLoader.getDescriptions()` 的结果。这样 system prompt 既可在编译期写死模板，又能在运行时根据实际工作区与可用技能动态注入。

### 3.4 工具定义的集中生成
所有工具定义通过内部 `tool(name, description, schema)` 方法生成，严格对齐 messages API 的 `{name, description, input_schema}` 结构。多阶段合并时使用 `dedupe()` 按 `name` 去重，保留最后一次定义，避免重复注册。

### 3.5 前端配置组织
- Next.js 配置文件位于 `web/next.config.ts`。
- 多语言文案以 JSON 文件形式存放在 `web/src/i18n/messages/`，由 `i18n-server.ts` / `i18n.tsx` 加载。
- 前端常量集中在 `web/src/lib/constants.ts`，用于 UI 行为控制。

## 4. 约定与约束

- **`.env` 仅用于本地开发**：注释明确标注 `ANTHROPIC_API_KEY` 需从 Anthropic 控制台获取；生产部署应通过系统环境变量注入，因为 `EnvConfig` 优先读取 `System.getenv`。
- **`MODEL_ID` 是强制必填项**：未设置时程序启动即抛异常，不允许静默失败。
- **新能力必须通过 `StageConfig.Builder` 暴露**：新增子系统开关应在 `StageConfig` 中增加对应 boolean 字段及 Builder 方法，并在相应 `sXX()` 中启用，而不是在业务代码中硬编码判断。
- **工具定义不得散落在各阶段类中**：所有工具 schema 必须通过 `StageConfig.tool(...)` 构造，保证格式一致且可被 `dedupe()` 处理。
- **system prompt 模板只含占位符**：具体工作区和技能信息必须在运行时由 `systemPrompt()` 注入，禁止在模板中硬编码绝对路径。
- **团队配置采用最小化 JSON**：`.team/config.json` 目前仅包含 `team_name` 与 `members` 数组，作为后续多 Agent 协作的可扩展配置点。

## 5. 总结

该仓库的配置系统围绕两个核心抽象：**`EnvConfig` 负责外部凭据与环境变量**，**`StageConfig` 负责 Agent 运行时能力的阶段化编排**。前者解决“连哪个模型、用什么密钥”，后者解决“当前阶段开放哪些工具、开启哪些子系统”。两者结合实现了 Claude Code 风格的教学式渐进演进——同一份 `AgentRuntime` 代码不变，仅通过切换 `StageConfig` 即可演示从 s01 到 s17 的能力叠加。
